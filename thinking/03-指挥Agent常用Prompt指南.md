# 指挥 Agent 常用 Prompt 指南（按工作阶段）

> 指挥 Agent 干活时，不同阶段最容易出的问题不一样：开局容易被讨好，动手前容易解错题，定方案时容易只看一条路，收尾时容易留下返工噪声。先在速查表里找到你现在在哪一步，再到对应小节挑一条复制。每条都能单独用，Claude、GPT 都适用。

## 速查表

| 阶段 | 什么时候翻这里 | 条目 |
|---|---|---|
| 一、开局定调 | 新开对话或新项目，想先立规矩 | 1–4 |
| 二、动手前：把问题想对 | 需求刚提出，还没开始做 | 5–11 |
| 三、找解法 | 问题清楚了，想要更好的思路 | 12–15 |
| 四、定方案前：证伪与推演 | 手上有个方案，准备拍板 | 16–20 |
| 五、执行与修复 | 正在做、在修 bug | 21–22 |
| 六、聊偏了：纠偏 | 越聊越不对劲、听不懂它在说什么 | 23–24 |
| 七、任务收尾 | 一个任务刚做完 | 25–27 |
| 八、定期治理项目 | 项目做了一阵，想清债、复盘 | 28–34 |
| 附：特定场景 | UI / UX 设计 | 35 |

## Prompt 原文

### 一、开局定调

**1. 开局定场**：对话一开始就说，让它全程不迎合、区分事实和推断。

```text
开局定场：请在与我的讨论和回答中遵循以下原则：以事实、证据和合理推理为依据，不因我的立场或偏好而迎合我，也不为反对而反对。如果我的观点、前提或推理存在问题，请直接指出并说明理由；依据不足或存在不确定性时，请明确说明，区分事实、推断与意见。表达应简洁、专业、重点突出，同时保留必要的解释和限定条件。
```

**2. 禁止讨好、要求无隐瞒**：怕它报喜不报忧、把做不到的事说成能做，同时想要更激进的发散。

```text
继续向我提问以确保你完全理解我的意思，且你的回答必须完全无隐瞒，禁止讨好我而隐藏“你做不到”的事实，你的回答可以犀利甚至有些“不安全”“偏执，疯狂的”
```

**3. 小白模式**：自己不懂技术，但要让它干代码的活。

```text
我是IT小白，啥也不懂，但又想干代码的事，请多帮我深度分析并用简单的语言表达
```

**4. 协作规则 15 条**：适合放进项目规则文件（CLAUDE.md / AGENTS.md）长期生效，而不是每次粘贴。

```text
与AI高效协作的15条规则:
1.先校准问题:区分目标、症状、原因和手段,发现问题定义有偏差就直说
2.从第一性原理出发:拆清目标、约束和完成标准,抓住关键原因。
3.意图清楚直接做,有实质歧义才提问,已回答的不重复问。
4.区分讨论与执行:问办法时比较方案,明确执行后自主推进。
5.方案写清收益、代价和适用条件,给出推荐,不为凑数制造选项。
6.重要方案先找反证,检查失败条件与适用边界,再作判断。
7.陌生问题先找成熟解法,必要时跨领域搜索,核实迁移成本。
8.推演改动的连锁影响,关注其他模块、使用行为和长期维护成本。
9.保持简单,优先现成工具和最短可验证路径,新增复杂度必须有收益。
10.只做授权范围内的事,先完成最小可用改动,不顺手扩大任务。
11.先查事实再下判断,说明资料覆盖范围,不把推测当事实。
12.简化前查清职责、依赖和设计意图,以新接手者能否理解检验结构。
13.验证力度匹配风险,分清已修改、已验证和已上线;写入结果未知时先核实。
14.被纠正先修当前问题,重复返工再查共因,将可预防的问题沉淀为规则或自动化。
15.决策权归用户,涉及费用、权限、发布和破坏性操作先确认;汇报先说结果,再给证据和必要下一步。
```

### 二、动手前：把问题想对

**5. 质疑问题定义**：怀疑自己提的问题本身就问偏了，症状当原因、手段当目标。

```text
不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来
```

**6. 理解真实目的，砍掉多余步骤**：你已经给了做法，但想让它判断这个做法是不是绕远了。

```text
不要只执行我的想法，要理解我的真正目的，主动质疑不必要的步骤，跳出现有框架，寻找更简单、更高效、更根本的解决方案。
```

**7. 先问清楚，再出三版方案**：需求有偏好成分（设计、文案、方案选型），想先对齐再挑。

```text
先问一些不清晰的问题，对齐我的喜好，然后再出3版方案。
```

**8. 动手前四问**：任务重要、反复做局部仍不满意，想让它先把方法和验证标准说清楚再做。

```text
动手前先去看一手材料，再答四问——这一行顶尖的人会多做哪一步（不做会错在哪）、从哪些能定位到的原件起手（不要汇总和别人的结论）、用什么叫得出名字的方法和工具、你我之外什么会说「不」的东西能证明结果对（写明什么结果算失败）——然后据此把任务改写成「交付物不变多、形态不变，只多出来源、方法和验证」的版本，给我看过点头后再做。
```

**9. 执行前先澄清**：需求里可能有模糊或缺失的信息，不想让它自己脑补。

```text
执行我的任务前，请先不要急着输出结果。
请你先识别我这个需求里所有模糊、缺失、可能影响结果的信息，并列出问题向我确认；等我补充完关键信息之后，你再正式开始执行。
如果你必须先做假设，请明确告诉我你做了哪些假设，不要自己偷偷脑补。
```

**10. 一次问一个，问到 95% 确信**：需求连自己都没想清楚，想被一步步问出来。

```text
在给出最终方案前，先向我提问。要求：一次只问一个问题，根据我的回答继续追问，直到你有95%的信心完全理解我的真实需求和目标，再给出最终方案
```

**11. 先判断要不要走完整流程**：重要、不可逆的决策用的完整版，自带准入判断，小问题它会直接说不用走。原评论换行有丢失，按原样保留。

```text
先别急着回答，也别默认我已经把问题想清楚。先判要不要走这套流程如果这个问题低风险、可逆、需求已经明确 → 直接告诉我"这个不用走流程"，然后正常回答。只有满足以下任一条才继续：影响面大、不可逆、返工成本按周算、我自己都没想清楚。
重述与纠偏用最完整的方式重述我真正想解决的问题——不是字面意思，是背后的真实困惑。如果我问错了问题，直接说，并告诉我应该问什么。挖出隐含假设列出我没说但已经默认成立的假设。标出哪些假设一旦不成立，结论就得推翻。
给出最强可行方案（不是正反二元）给 2-4 个方向，不要强行分成支持和反对两派——那样会挤掉可能最优的第三条路。每个方向说清：最强论证（必须基于可验证事实；属于推测的明确标注）什么条件下它是最优解代价、风险、我需要付出什么约束：不为了凑数造弱方案。不把薄弱想法包装得很精致——逻辑完整但事实悬空的方案比没有方案更危险。
找关键分歧各方案真正的分歧点在哪里？然后回答一个问题：如果只能改变一个假设就能翻转最终结论，那个假设是什么？
缺什么信息你能自己查或验证的 → 直接去查，别拿来问我只有我知道、且会改变结论的 → 问我，一次只问最关键的那一个如果信息已经够了，跳过这步直接给结论。
结论信息够了才给。包含：值得做 / 需要改 / 应该放弃最大风险是什么最缺的关键证据是什么今天就能执行的最小一步置信度（百分比 + 凭什么）
```

### 三、找解法

**12. 是不是别的领域的经典问题**：碰到新问题，先查有没有现成的成熟解。

```text
我的想法或目前存在的问题是否是其他领域经典问题的变体，有无成熟的解决方案，请进行跨领域的广度搜索核实这一点
```

**13. 跨领域找最优解**：比第 9 条更开放，不只核实，而是主动借鉴别的领域。

```text
其他领域里有没有类似的方案，用跨领域的方式全面思考，找到最优解。
```

**14. 看开源项目怎么解**：技术问题，想参考别人已经踩过的路。

```text
去 GitHub 上查一下相关热门开源项目，这种问题是如何解决的
```

**15. 辩证推演、穷举可能性**：想把可能性铺开，而不是直接收敛到一个答案。

```text
请按照辩证法和二元辩论对结果进行反复推演并优化，请按照联想的基本原理还有遍历法找出尽可能多的可能性
```

### 四、定方案前：证伪与推演

**16. 站在最强反对者角度**：它给了方案、你也觉得不错，拍板前让它自己推翻一遍。

```text
先假设你当前认为最合理的方案是错误的。站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况。然后重新评估方案，看看有没有更好的解法。
```

**17. 推演二阶、三阶影响**：改动会波及其他模块或用户习惯。

```text
不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。
```

**18. 边界异常压力测试**：要它在下结论前先列反例，适合推理类问题。

```text
请执行深层推演（Level: xHigh）。在生成最终结论前，先列出至少 3 种边界异常与假设推翻场景，逐一进行逆向压力测试，确认逻辑无误后再输出解决方案。
```

**19. 像法官一样审视**：一句话版，随手加在要求后面。

```text
像个法官一样审视各项重要的逻辑节点
```

**20. 结论五要素带置信度**：要它拍板时，规定结论必须包含哪几项，并说出把握有多大。

```text
最终结论请包括:
1.这个想法值得做、需要改，还是应该放弃;
2.最大风险是什么;
3.最缺的关键证据是什么;
4.今天可以执行的最小一步是什么;
5.你的置信度是多少。
记住:准确性高于让我满意。不要无脑夸我，不要顺着我说。不确定就说不确定，不要编答案。
```

### 五、执行与修复

**21. 第一性原理修复**：修 bug 时不要只打补丁。

```text
从第一性原理出发，找到最本质原因，修复一下。
```

**22. 别犯惯性错误**：一句话版，随手加在任务后面。

```text
别犯各种ai惯性错误
```

### 六、聊偏了：纠偏

**23. 独立重新评估**：讨论了很多轮、越聊越不对劲，让它跳出来重新判断，不迁就你之前的意见。把 XXXXX 换成讨论的主题。

```text
请重新回顾此前围绕 XXXXX 的设计讨论，独立重新评估该设计的取舍，并判断什么才是最佳方案；不要因为那些建议由我提出就倾向于接受，也不要为了迎合我而让步。给出你独立得出的推荐设计，说明理由、关键取舍和仍存在的不确定点或需要补充验证的信息。
```

**24. 说人话**：它的回复太绕、术语太多。

```text
我听不懂你说的，直白一些。
```

### 七、任务收尾

**25. 独立核验**：做完后问它，哪一步验证真能抓出错误。

```text
如果其他几方都错了，你这次做的哪项独立核验，有机会发现那个错误。
```

**26. 去掉返工噪声**：长期维护的项目，防止它把试错过程、返工痕迹留进文件变成技术债；一次性任务可不加。

**变体：任务进行中就要求**

```text
尽量保证低熵运行，确保任务中不留存非必要的上下文噪声、历史返工噪声，仅保留正向流程。
```

**变体：任务做完后检查**

```text
请检查刚刚的任务，确保任务中不留存非必要的上下文噪声、历史返工噪声，仅保留正向流程。
```

**27. 收尾两问**：任务做完，让它主动补漏、给下一步。

```text
接下来你建议做什么？
```

```text
你还有什么问题么？
```

### 八、定期治理项目

**28. 识别历史包袱**：项目做久了，想知道哪些设计可以安全删掉。

```text
深入分析整个代码库的Git历史、关键PR和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
```

**29. 新人接手的认知成本**：想让项目更好懂、更好交接。

```text
假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。
```

**30. 凭第一感觉找弯路**：怕文档把它带偏，让它不看文档直接看代码挑毛病，只诊断不动手。

```text
忽略项目中所有文档，从第一感觉出发，告诉我项目在设计中存在的弯路与技术债务。并且联网搜索优秀的开源案例分享给我。不要上手修改。
```

**31. 全项目清理**：AI 留了一堆过程记录、废弃版本，想一次清干净。

```text
请全面检查当前项目的所有文件（包括脚本、文档等），完成以下工作：逐项审查并确认代码结构干净、命名与结构统一归一、遵循单一职责原则；删除冗余内容、废弃的历史记录及历史思考过程，仅保留最终敲定的版本；最后对所有修改进行审核，并汇总说明发现的问题、已做的清理与调整，以及是否还存在潜在冗余或待确认的取舍。
```

**32. 找出最慢的 PR**：把 XX 换成天数。

```text
全面分析最近XX天里的所有的PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。
```

**33. 复盘返工的共同根因**：同样的问题反复出现，想沉淀成规则或自动化。把 XX 换成时间范围。

```text
全面复盘最近XX时间的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者Skill，避免我们反复支付同样的成本。
```

**34. 改进我自己的常用指令**：让它翻你最近的对话，帮你把常说的话改得更好。

```text
请帮我翻了一下最近两个月，我指挥Agent干活，最爱说的几句Prompt，怎么说会更好
```

### 附：特定场景

**35. UI / UX：功能收束 + 去 AI 味**：做界面设计时分两步用。

```text
1. 从产品经理的角度去对整体功能需求进行收束，梳理一份核心功能架构，出一个mermaid的功能流程图。
2. 【洗掉ai味】从用户体验的视角，去对整体产品UI、UX设计做优化，去掉无用说明、改掉用户不懂的晦涩文字、最大程度简化用户操作，优化后使产品达到可交付的标准状态。
```
